# ADR-0003 V1.0.0 先做好 GitHub 仓库理解

## 状态

已接受

## 背景

V1.0.0 原计划把 arXiv / GitHub 作为一手材料输入，并把 JD 作为可选岗位偏置。

后续讨论认为，JD 会把系统拉向“岗位匹配”，但当前产品真正需要先验证的是“系统能不能读懂用户真实项目”。如果仓库理解不准，JD 只会让输出看起来更岗位化，并不能提升项目拷打质量。

DevContext.AI 的架构证明了“仓库分析 -> 项目报告 -> 项目面试”这条路线可行。但本项目不能只做软件工程仓库体检，而要面向实习、保研、研究岗里的项目考核。

## 决策

V1.0.0 先聚焦 GitHub 仓库理解。

V1.0.0 必要输入：

- GitHub 仓库链接

V1.0.0 可选补充：

- 用户负责的模块
- 目标方向
- 希望重点检查的代码路径

后置能力：

- V1.1：JD / 岗位描述偏置
- V1.2：arXiv / 论文项目理解
- V1.3：实时面试追问

## 后果

正面影响：

- Demo 范围更清楚。
- 实现优先级更稳。
- 可以把最核心的仓库理解能力做深。
- 更容易和 DevContext.AI 对比出差异：我们不是仓库体检，而是项目考核。

代价：

- V1.0.0 暂时不能按 JD 定制面试。
- V1.0.0 暂时不能处理纯论文项目。
- 后续需要重新接入 JD 和 arXiv，但它们会建立在仓库理解能力之上。
