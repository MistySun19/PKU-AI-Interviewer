# Traceback 视频演讲稿

## 标题

你的 GitHub 项目，哪里会被面试官问穿？

## 演示节奏

- 0:00 - 0:30：先展示 Demo wow moment。
- 0:30 - 2:30：切到介绍页，解释产品和 agent 设计。
- 2:30 - 3:00：回到 Demo，展示 Evidence Check 和持续追问。

## 演讲稿

大家好。

今天我想讲一个问题：

你的 GitHub 项目，真的经得起面试官追问吗？

有了 vibe coding，AI 项目变得越来越容易做。README 可以写得很好看，简历也可以。

但项目面试，不只是看你写了什么，也不是听你泛泛讲一遍项目。真正的项目面试看的是：

你说自己做过的东西，能不能在仓库里找到证据。

好的技术面试官会顺着你的 claim 继续深究，直到确认一件事：

这个项目，到底是不是你真的理解、做过、能解释。

所以我们做了 Traceback。

你给它一个 GitHub repo，它告诉你：

这是你的项目里最可能被面试官问穿的地方。

界面很简单。

左边，是会被问穿的风险点。

右边，是代码、README 或配置证据。

这个产品不是帮学生生成更多题，而是帮学生发现：

我项目里哪些地方思路理不清，哪些 claim 没有证据，哪些实现细节一追就会露怯。

整个系统分成三部分。

第一部分是 Deep Research Agent。

它不直接出题，而是先搜索仓库、读懂仓库。它会看 README、核心代码、配置、训练入口、评测逻辑和数据处理，最后整理出项目理解地图：

整个项目声称做了什么，证据在哪里。

第二部分是 Evidence Check Agent，也是最关键的设计。

AI 很容易生成听起来专业、但证据不扎实的风险点。所以每一个风险点进入结果之前，都要经过这个 Agent。

它检查两件事：

第一，证据是否充分。

reference 能不能支撑这个问题、这个 claim、参考答案和红旗回答。

第二，证据是否必要。

每一条 reference 是否真的对判断这个风险点有贡献，还是只是关键词相关。

如果证据不够，系统不会强行把这个问题放进最终结果。

最后一部分是输出和追问。

最终系统输出的不是一套泛题，而是将前面两者连起来，生成真正有价值的项目面试风险点与证据。

用户可以点开任意一个风险点，尝试回答，然后 Agent 会继续追问。

这更接近真实面试：

你哪里答得虚，面试官就往哪里追；你哪里讲得清楚，面试官就换一个角度继续验证。

这就是 Traceback。

它让学生在真正面试前，先被 AI 面试官通过不断追问发现短板，接着补自己的项目理解。

以前，学生准备项目面试，是找 AI 生成一些题，然后背答案。

现在，我们希望它变成：

给出一个 repo。

系统找出最可能经不住追问的地方。

每个地方都有代码证据。

学生逐个练，逐个补。

直到项目真的经得起追问。

现在，请把 repo 给它。
