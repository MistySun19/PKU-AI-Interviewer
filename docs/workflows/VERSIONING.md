# 版本管理规则

本项目同时维护三类记录：

1. `CHANGELOG.md`: 对外可读的版本变化。
2. `VERSION_WORKLOG.md`: 产品定位和版本演化过程。
3. `docs/adr/`: 架构和产品决策记录。

它们分工不同，不能互相替代。

## 版本号约定

使用语义化版本的精神，但早期允许计划版本：

- `v0.0.1`: 产品定位和调研版本。
- `v1.0.0-plan`: V1.0.0 架构计划。
- `v1.0.0`: 第一版可运行产品。
- `v1.1.0`: 增加实时面试追问。
- `v1.2.0`: 增加题库向量检索。
- `v1.3.0`: 增加题库定时更新。

Git tag 等真正发布时再打，不要给纯想法随意打 tag。

## 什么写进 CHANGELOG

写入：

- 新增功能。
- 重要架构变化。
- 用户可见变化。
- 重要流程变化。

不写入：

- 细碎错别字。
- 中间推理过程。
- 未确认的想法。

## 什么写进 VERSION_WORKLOG

写入：

- 产品定位变化。
- 版本之间的关系。
- 为什么从一个方向转到另一个方向。
- 哪些旧假设被保留，哪些被放后。

不写入：

- 具体代码实现细节。
- 过长调研原文。

## 什么写进 ADR

ADR 是 Architecture Decision Record，也可以记录关键产品架构决策。

适合写 ADR 的情况：

- 必要输入从“项目描述”改为“arXiv / GitHub”。
- 决定用 `kaomian` 作为题库快照。
- 决定暂时不接入 `bagu-killer` 主流程。
- 决定先生成报告，不先做聊天。

## 新版本创建流程

1. 先写或更新计划文档。
2. 如果定位变化，更新 `VERSION_WORKLOG.md`。
3. 如果对外可见，更新 `CHANGELOG.md`。
4. 如果是关键架构选择，新增 ADR。
5. 更新 `README.md` 和 `AGENTS.md`。
6. 创建提交。

## 后续发布检查清单

发布前确认：

- README 能解释当前产品是什么。
- AGENTS 能指导后续智能体继续工作。
- CHANGELOG 有对应版本条目。
- VERSION_WORKLOG 记录了版本关系。
- 关键决策有 ADR。
- 代码能本地运行。
- 公网 URL 可访问。
