# 24 Hours Reflection：从 AI 面试工具到 Traceback

从晚上拿到这个题目开始，我第一件事不是直接写代码，而是去请教了很多正在实习或刚经历过面试的同学和朋友。他们向我详细讲了真实面试里的流程、现场情况，以及当时最难应对的地方。

这些交流很快让我抓到了一个共同痛点：面试官在追问项目时，往往不是停留在“你做了什么”，而是会继续追到非常细的实现细节、设计理由和边界条件。

比如一个项目里某个模块为什么这么设计、某个参数是怎么构造的、某个流程在真实场景下会不会失效、某个 claim 是否真的能在代码里找到证据。这些问题不是靠背通用题库就能解决的。

与此同时，我观察了现在很多 AI 面试产品。它们大多更像“豆包”式的 AI 视频通话：用户和 AI 进行一场模拟面试，AI 负责提问、追问和反馈。但我发现，这类产品往往没有真正利用一个非常关键的信息源：代码仓库。

对技术项目面试来说，GitHub repo 其实是极佳的一手材料。README、配置、核心代码、评测脚本、数据处理和运行入口，都能反映一个项目到底做了什么，也能暴露候选人是否真的理解自己的项目。

于是我开始想：能不能只提供一个 GitHub 链接，就让系统基于代码仓库生成并复现一套完整的项目面试流程？

基于这个想法，我搭建了一整套 Agent Pipeline。系统先抓取仓库，再规划研究维度，之后并行深读代码，最后生成项目理解和面试问题。

但到下午时，我遇到了一个非常棘手的瓶颈：

> 如果这件事只是把 GitHub 链接交给 ChatGPT 就能完成，那用户为什么还需要我的软件？

这个问题让我卡了很久。我不断和 GPT 讨论这个项目的核心重点，以及在 AI 持续进步之后，什么东西才是不会被轻易替代的。

在这个过程中，我非常感谢红杉资本和“第一性原理”给我的启发。我围绕几个关键词反复思考：

1. 壁垒是什么？
2. 可达性（Accessibility）如何？
3. 传播度（Diffusion）怎么样？

我的反思是：

第一，壁垒是最关键的问题。我之前那一版几乎没有壁垒。只要 GPT 读代码的能力足够强，它就能实现一个类似的面试流程。这对产品来说非常致命。

第二，可达性是用户能不能一眼看懂这个软件在做什么。一个好的产品不应该要求用户先读懂一套复杂概念。用户应该很快看到：左边是可能被问穿的问题，右边是代码证据。

第三，传播度取决于目标人群是否足够多，以及他们是否意识到 AI 正在改变项目开发和面试准备方式。对 AI、算法、研究岗和 Agent / RAG 方向的学生来说，这个问题已经很明显：vibe coding 让项目更容易做出来，但也让“是否真的理解项目”变得更值得被验证。

观察下来，第二点和第三点基本成立。真正需要解决的是第一点：壁垒。

由此，我想到了一套更像代码编辑器或审查器的产品框架。ChatGPT 本身可以读代码、总结代码，但它不会天然给用户提供一个结构化的 evidence-linked workflow。它不会像一个工具一样，把“会被问穿的问题”和“代码证据”并排呈现，也不会稳定地帮用户判断每条 evidence 是否足够支撑问题。

所以我把产品重新设计成 Traceback。

Traceback 的核心不再是“AI 生成面试题”，而是：

```text
repo 证据 -> 面试风险点 -> 代码定位 -> 参考答案 / 红旗回答 -> 持续追问
```

我让 GPT 作为生产力核心，负责理解仓库和生成候选风险点；但在它之后，我又设计了验证 Pipeline，也就是 Evidence Check Agent，专门检查 reference 是否充分且必要。

这一步很重要。因为只有真实、准确、可定位的证据，才能真正帮助学生复习。如果 AI 提了一个听起来很专业的问题，但 evidence 根本不能证明这个问题，那它反而会误导用户。

此外，我也意识到，如何让学生方便地查看这些问题，本身就是一个壁垒。它不是单纯的知识领域门槛，而是视觉和交互门槛。用户不应该面对一大段报告，而应该看到一个清晰的审查界面：

- 左边是最可能被面试官问穿的地方。
- 右边是代码、README 或配置证据。
- 每个问题下面可以继续回答，系统继续追问。

这就是我最终做出 Traceback 的原因。

复盘这 24 小时，我最大的感悟是：做 AI 产品必须从第一性原理出发。

第一，要找到用户真正的核心需求。用户不是缺少更多题目，而是缺少一种方式，在真正面试前知道自己的项目哪里经不起追问。

第二，在 AI 时代做产品，必须不断把自己和 AI 本身比较。不能只问“AI 能不能做这件事”，还要问：

> 半年后的 AI 变强以后，我的产品还有什么不可替代的部分？

对 Traceback 来说，我目前的答案是：单纯的生成能力不是壁垒，壁垒在于 evidence-linked workflow、证据验证、交互呈现，以及让用户能围绕真实代码持续补自己的理解。

第三，真正有价值的切入点，往往不是和 AI 比谁更聪明，而是设计一个系统，让 AI 的能力被组织进一个用户真正需要的流程里。

这 24 小时让我更深地意识到：AI 产品不是把一个 prompt 包装成软件，而是要找到 AI 能力和用户真实场景之间那个最锋利的接口。

Traceback 就是我这次找到的接口。
