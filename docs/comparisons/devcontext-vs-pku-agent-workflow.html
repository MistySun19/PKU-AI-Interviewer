DevContext.AI 与 PKU AI Interviewer 的 Agent Workflow 对比

DevContext.AI 的架构值得借鉴，因为它已经把“仓库分析 -> 项目报告 -> 项目面试 -> 回答评价”跑成了闭环。 但 PKU AI Interviewer 的目标不是复刻一个软件工程仓库解释器，而是做面向实习、保研、研究岗的项目考核拷打器。

核心差异

他们问“这个软件项目工程上做得怎么样”；我们先问“系统能不能读懂这个仓库，并找到面试官会追的项目考核点”。

DevContext.AI Workflow

输入 GitHub 仓库，生成招聘友好的工程项目报告，并进入项目相关文字面试。

Repo Analyzer

  1. Repository Processing

    克隆仓库，过滤依赖、构建产物、二进制和 boilerplate，保留用户代码。

  2. Stage 1 Project Review

    评估代码质量、架构清晰度、复杂度、生产可用性和真实性信号。

  3. Stage 2 Intelligence Report

    生成架构报告、设计决策、技术取舍、可扩展性和简历要点。

  4. Stage 3 Interview Simulation

    生成项目专属题目，分为 project understanding、implementation、domain expertise、edge cases、scaling。

  5. Answer Evaluation & Follow-up

    用户文本回答后，系统即时评分；如果回答浅或漏点，则生成动态追问。

PKU AI Interviewer Workflow

V1.0.0 先输入 GitHub 仓库，生成面向项目考核的证据驱动面试计划；JD 和 arXiv 后置。

Project Examiner

  1. Input Parsing

    校验 GitHub 仓库链接，解析 owner、repo、branch 和用户补充的负责模块。

  2. Evidence Ingestion

    抓 README、文件树、核心代码、配置、测试、评测脚本和示例材料；保留可引用证据。

  3. Material Understanding

    理解项目目标、主流程、核心模块、数据流、agent loop、评测、异常处理和部署边界。

  4. Examiner Review

    像认真面试官或导师一样找追问点：设计理由、细节缺口、实验可信度、失败场景和真实贡献。

  5. Bagu Retrieval & Interview Plan

    用 kaomian 召回高频八股，再把八股改写成绑定仓库证据的追问链。

关键维度对比

维度 DevContext.AI PKU AI Interviewer 我们的产品判断
核心对象 GitHub 软件工程仓库。 V1.0.0 先聚焦 GitHub 仓库；arXiv、JD、笔试题复盘进入后续版本。 先把仓库理解做深，再扩展到更多项目证据。
主要用户 工程毕业生或软件工程候选人，想把项目讲成招聘语言。 AI、算法、研究岗实习候选人，以及保研找导师的学生。 用户焦虑不是“报告好不好看”，而是“被追问时会不会露馅”。
证据粒度 强调文件、函数、代码模式、行号引用。 V1.0.0 需要 README、文件、函数、模块、测试、评测和运行路径证据。 先做到 repo-grounded，再扩展到 paper-grounded 和 JD-grounded。
问题类型 架构、实现、取舍、边界情况、扩展性、代码质量。 项目事实、设计理由、核心实现、评测可信度、八股连接、失败场景、真实贡献。 我们要保留工程深挖，但用项目考核标准重写它。
实时面试 文字作答，提交后即时评分，根据弱点生成 follow-up。 V1.0.0 先生成面试计划；V1.3 再做基于回答的连续追问。 先把题出准，再做聊天；顺序很重要。
题库角色 主要从仓库上下文生成项目问题。 kaomian 作为高频八股校准器，bagu-killer 未来做题库更新流水线。 题库不能直接拼题，必须和材料证据绑定。

我们应该借鉴什么

直接借鉴：分阶段流水线

先处理材料，再结构化理解，再生成面试内容。这个顺序能避免模型直接泛问，也方便展示进度。

Stage pipeline Progressive output
直接借鉴：证据绑定

每个结论和问题都要引用来源。V1.0.0 先绑定 README、代码文件、核心模块、测试和评测证据。

Grounded claims Evidence source
直接借鉴：回答评价闭环

V1.3 可以采用“回答 -> 评分 -> 判断缺口 -> 追问”的机制，让拷打变成连续回合。

Answer scoring Dynamic follow-up
需要改造：领域理解

他们的领域理解偏软件工程；我们需要先让 agent 在仓库里识别 RL、RAG、后训练、具身智能、eval benchmark、合成数据等方向痕迹。

AI research Paper-aware
需要改造：问题生成标准

不能只问工程扩展性，也要问评测是否可信、方法为什么成立、细节为什么这么设计、哪些地方会被面试官质疑。

Project exam Research defense
不要照搬：软件工程单一视角

如果只做代码质量报告，我们会和 DevContext.AI 过于接近。我们的差异是“项目考核”，不是“仓库体检”。

Avoid clone Keep positioning

PKU AI Interviewer 的推荐 V1.0.0 Agent Loop

1. 解析输入

识别 GitHub 仓库，解析仓库元信息和用户负责模块。

2. 抓取证据

获取 README、文件树、关键代码、测试和评测材料。

3. 审查材料

找真实面试官会追问的风险点。

4. 连接题库

召回 kaomian 高频题并绑定项目证据。

5. 生成计划

输出题目、证据、期望回答、红旗和追问链。

一句话结论

DevContext.AI 证明了“读仓库生成面试”这条技术路线可行；PKU AI Interviewer 的 V1.0.0 先把仓库理解做深，再把这条路线推进到更贴近中国学生真实场景的项目考核：代码、八股、评测、真实贡献和导师/面试官式连续追问。
