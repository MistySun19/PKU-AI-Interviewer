# PKU AI Interviewer 项目开发记录

这份记录写的是 V1.0.0-beta 之前和当前这一段开发过程。它不是最终产品介绍，而是给后续开发者、评审者和自己回看的一份过程备忘。

## 1. 起点：不是再做一个通用题库

项目最早的问题意识很简单：很多 AI、算法、研究岗候选人并不是没有刷题，而是对自己的项目没有被系统性追问过。

普通模拟面试往往让用户先描述项目，然后生成一些泛问题。这样做很快，但问题容易漂浮在项目之外。真正有压力的项目考核通常不是问“你用了什么模型”，而是沿着项目证据一直追：

- 这个 claim 在代码哪里实现？
- 训练、推理、评测路径能不能串起来？
- 指标和 baseline 是否支撑 README 或论文里的说法？
- 如果数据、超参、seed 或场景变了，方法还站得住吗？
- 哪些部分最像“你可能没真正做过”的风险点？

所以项目定位逐渐从“AI 面试题生成器”转向“仓库理解优先的项目考核面试生成器”。

## 2. 输入收敛：GitHub 仓库成为主入口

V1.0.0 的关键取舍是把 GitHub 仓库链接作为必要输入，把用户手写项目描述降级为补充材料。

原因是项目考核面试的核心证据不应该只来自用户自述。README、代码、配置、训练脚本、评测脚本、数据处理和测试文件，才是更稳定的一手材料。

这个阶段形成了几条工程原则：

- 不先做登录、语音、视频或大型数据库。
- 不把 JD、arXiv 解析和泛题库页面放进 V1.0.0 主线。
- 先用 GitHub REST API 抓取公开仓库，不做 `git clone`。
- README 作为重要原始证据完整进入模型上下文。
- 模型请求不主动设置 `max_tokens`，避免面试计划被截断。

## 3. alpha：先跑通仓库基础理解

alpha 阶段实现了最小闭环：

1. 用户输入公开 GitHub 仓库。
2. 系统解析 owner、repo、branch。
3. 抓取 README、文件树和关键文件。
4. 按文件名和目录优先级筛出代码、配置、训练、评测、测试等材料。
5. 生成一份基础项目考核计划。

这个版本验证了方向，但也暴露了问题：如果只是把一批文件一次性交给模型，输出很容易变成泛化总结。模型知道这是一个项目，但不一定真正读懂“方法、训练、评测和复现”之间的关系。

## 4. alpha.1：转向 paper-code 和 AI 项目制仓库理解

alpha.1 把重点从通用软件工程审查转到论文 / AI 项目制代码库。

这个阶段明确：不要在 ingest 阶段靠正则硬判 paper signals，而是让模型基于 README、链接、文件树和代码证据判断仓库形态。对 paper-code 或 AI 项目制仓库，系统要拆出：

- 问题设定
- 论文或 README 的核心 claim
- 方法实现代码
- 训练入口和配置超参
- 推理 / demo 路径
- 数据处理逻辑
- 评测、消融、benchmark 和复现路线

这一版也开始把“导师式追问”的标准写进产品规则：面试计划不能只问会不会八股，而要问 claim 和代码是否一致、评测是否支撑结论、哪里可能有数据泄漏或复现风险。

## 5. beta：Repo Deep Research Agent

beta 的核心变化是把单轮分析拆成 Repo Deep Research Agent 管道：

1. Scout：抓取仓库元数据、文件树、repo map 和关键证据。
2. Plan：规划研究维度，判断仓库形态，给每个维度分配文件。
3. Research：多个 digest worker 并行深读不同维度，必要时补读文件。
4. Synthesize：合成完整项目理解报告。
5. Questions：连接 `kaomian` 高频题库，生成绑定仓库证据的项目考核点和题目种子。
6. Module Hub：分析完成后，再进入 Survey、练习和测试三个模块。

这一版里，`kaomian` 的定位也被重新约束：它不是主线，不允许直接把题库题拼进输出。正确用法是先从仓库证据中找到风险点，再用题库提供高频面试连接，最后改写成项目相关追问。

## 6. Interactive 提前落地

原本实时追问不是 V1.0.0 的主线，但在 beta 阶段被提前做进来。

后续产品判断进一步收敛为：分析不应该等同于 Survey，也不应该在入口处就让用户选择 Survey / Interactive / Practice。更自然的流程是先统一分析仓库，再把同一份项目理解分发给三个模块：

- Survey：给出项目细节地图、证据来源、可问细节和题目种子。
- Practice：基于当前分析结果生成一套新的练习题，允许提示和参考答案。
- Test：基于当前分析结果生成一套新的测试题，不给提示，结束后输出详尽复盘。

Interactive / Test 模式复用同一份仓库理解，进入一问一答：

- 给出第一题。
- 根据回答强弱打分。
- 弱回答触发追问。
- 到达题数或结束条件后生成逐题复盘和补坑计划。

这个阶段也暴露了很多产品和工程问题：模型配置、thinking 模式速度、服务端环境变量、流式状态、前端渲染、等待反馈、降级报告提示，都需要在真实测试中反复修。

后续测试中又暴露出另一个产品问题：如果只有测试功能，用户会被问题击中，但不一定知道怎么补。于是新增了 Practice 练习模式。Practice 仍然使用仓库证据和追问链，但用户可以请求 AI 生成提示或参考答案，从“被拷打”进入“学会怎么回答”。

同时，刷新丢失进度的问题被拆成两层处理：

- 前端用 `localStorage` 保存报告草稿、题目、聊天记录、runId 和 session 快照。
- 服务端用 `runId` 保存分析事件历史，刷新后可以回放已发生事件并继续订阅后续事件。

这不是最终数据库方案，但已经能覆盖 beta 阶段最影响体验的刷新中断问题。

## 7. 当前版本的真实测试记录

开发到这一版时，我刚刚用软件真实测试了一轮，发现它还有非常多问题。

有些地方还会卡住；有些报告会降级；有些状态提示不够清楚；有些结果的渲染还不够像一份真正可读的面试计划。更重要的是，我在回答它的问题时，很多东西答得奇奇怪怪，甚至根本答不上来。

但也正是在这一轮测试里，我第一次非常明确地感到了这个产品的 wow moment。

它提出的一些面试题非常有见地，而且一针见血。很多问题不是泛泛地问技术名词，而是直接扎到项目里最容易被追问、最容易暴露准备不足的地方。那种感觉很强烈：软件还远远不完美，但它已经开始像一个认真读过项目的面试官，能逼你意识到自己到底哪里没讲清楚、哪里没有证据、哪里经不起追问。

这件事很重要。它说明当前版本虽然粗糙，但核心价值已经出现了：

- 它能让用户从“我以为我懂自己的项目”切换到“我能不能经得起追问”。
- 它能把仓库里的方法、代码、评测和八股知识连成具体问题。
- 它能在真实面试前制造一种有用的压力感。
- 它能暴露用户自己都没意识到的知识空洞。

这也是接下来继续迭代的信心来源。

## 8. 当前欠账

这一版之后，最需要补的不是大功能，而是把已经出现的价值变得稳定、可读、可复现：

- 报告渲染：项目考核计划要突出重点，把次要信息后置，避免整页 Markdown 堆叠。
- 进度反馈：让用户知道现在是抓仓库、并行深读、合成报告，还是出题。
- 模型配置：测试阶段默认使用 DeepSeek V4 Flash / Pro 的 non-thinking 模式，提高迭代速度。
- 降级提示：没有 API key 或模型失败时，必须明确告诉用户当前结果是降级报告。
- 证据质量：每个核心问题都要尽量绑定文件、路径、配置或 README 片段。
- 回归评测：建立 golden repo 集合，持续检查报告质量和问题质量。
- Practice / Test 稳定性：题集生成、追问、提示、参考答案、复盘和 session 状态要能长时间稳定工作。
- 持久化升级：当前 `runId` / `localStorage` 方案适合 beta；后续如果要跨设备、跨部署恢复，需要数据库或 Redis。

## 9. 当前判断

PKU AI Interviewer 还不是一个完成品。它现在更像一个已经证明方向的 beta 原型。

但这次测试留下的最重要判断是：只要它能持续生成这种有证据、有压力、一针见血的问题，这个产品就不是普通题库，也不是普通代码审查工具。它更接近一个“项目考核前的高压复盘器”。

接下来的迭代目标，是把这个 wow moment 从偶发体验变成稳定体验。
