# Traceback 项目开发记录

这份记录是给后续开发者和评审者看的过程备忘。最终产品介绍以 `README.md`、`PRODUCT_MEMO.md` 和 `docs/demo-video-script.md` 为准。

## 1. 起点：项目面试不是泛题库

最初的问题意识是：很多 AI、算法、研究岗候选人并不是没有刷题，而是对自己的项目没有被系统性追问过。

普通模拟面试让用户描述项目，再生成一些泛问题。这样很快，但问题容易漂浮在项目之外。

真正有压力的项目考核会沿着仓库证据追：

- 这个 claim 在代码哪里实现？
- 训练、推理、评测路径能不能串起来？
- 指标和 baseline 是否支撑 README 或论文里的说法？
- 如果数据、超参、seed 或场景变了，方法还站得住吗？
- 哪些部分最像“你可能没真正做过”的风险点？

## 2. 输入收敛：GitHub 仓库成为主入口

V1 的关键取舍是把 GitHub 仓库链接作为必要输入，把用户手写项目描述降级为补充材料。

原因很直接：项目考核的证据不应该只来自用户自述。README、代码、配置、训练脚本、评测脚本、数据处理和测试文件，才是更稳定的一手材料。

## 3. Repo Deep Research Agent

早期单轮分析很容易变成泛总结。后来把仓库理解拆成四阶段：

1. Scout：抓取仓库元数据、文件树、repo map 和关键证据。
2. Plan：规划研究维度，判断仓库形态，给每个维度分配文件。
3. Research：多个 digest worker 并行深读不同维度，必要时补读文件。
4. Synthesize：合成完整项目理解地图。

这一步证明了系统能比“直接把 repo 链接丢给 ChatGPT”更认真地读项目。

## 4. 完整平台尝试

beta 阶段曾经把产品做成完整平台：

- 项目细节地图。
- 练习。
- 测试。
- 追问。
- 评分。
- 复盘。
- 历史记录。
- `kaomian` 连接。

这证明工程能力是够的，但也暴露了产品问题：范围太大，还没有先证明最小闭环。

## 5. 收缩为 Traceback

关键质疑是：

> 这个软件和 ChatGPT 加一个 GitHub 地址，到底有什么区别？

新的答案是：

Traceback 不只是生成题。它要做的是：

```text
repo 证据 -> 面试风险点 -> 代码定位 -> 参考答案 / 红旗回答 -> 持续追问
```

因此产品从“AI 面试平台”收缩为“Repo 面试风险审查器”。

## 6. Evidence Check Agent

自测时发现一个严重问题：模型找的 evidence 有时只是相关，但不能完全验证问题。

例如：

- `distributed_attention.py` 能证明存在 `tensor_split`、`all_to_all`、`DistributedAttention.forward`。
- 但它不能直接证明变长序列不均匀时如何处理 padding、GPU 空转或显存浪费。
- `cu_seqlens` 真正出现在非分布式 varlen 分支，不能说它是在 DistributedAttention 里构造的。

这促成了 Evidence Check Agent：

- 检查 reference 是否充分。
- 检查 reference 是否必要。
- 不充分的问题不能进入最终结果。

新的原则是：

> 先说代码事实，再问风险；不能把 evidence 没证明的东西写成实现事实。

## 7. 当前界面

当前界面是双栏 viewer：

- 左侧：会被问穿的问题。
- 右侧：代码 / README / 配置证据。

每个风险点下有：

- 对应 claim。
- 参考答案。
- 红旗回答。
- 补坑建议。
- Evidence Check。
- 回答框和持续追问。

首页右上角提供：

- `Demo`
- `介绍`

用于先展示 wow moment，再切到介绍页讲产品。

## 8. 当前欠账

最需要补的不是大功能，而是稳定性和证据质量：

- 为演示 repo 固定结果，保证 1 分钟内展示。
- 建立 golden repo 回归集。
- 继续降低 import-only、README-only、泛相关 evidence 误入最终结果的概率。
- 打磨右侧 Evidence Viewer。
- 打磨单风险点追问质量。

## 9. 当前判断

Traceback 的价值已经从“生成面试题”变成了“发现项目面试风险”。

如果系统能稳定抓到真实、具体、有代码证据的问题，它就不是普通题库，也不是普通代码审查工具，而是一个面试前的项目风险审查器。
